# ARBOR I - Visual Design Language

**Status:** North Star / pre-data design direction  
**Product:** Gaia Skill Tree  
**Tree:** Arbor I  
**Purpose:** Define the visual and interaction language for Arbor before the full capability graph and interaction-edge data are available.

---

## 1. Design thesis

Arbor is not a reskin of Yggdrasil.

Arbor is a different projection of the same Gaia capability universe.

Yggdrasil answers:

> What has this capability structurally become, and what standing has it earned?

Arbor answers:

> What does this capability do to an agent, and what happens when it interacts with other capabilities?

Therefore the two Trees should feel related, but governed by different visual physics.

```text
                     GAIA CAPABILITY WORLD
                              │
                ┌─────────────┴─────────────┐
                │                           │
                ▼                           ▼
         YGGDRASIL III                   ARBOR I
            prestige                    capability
            standing                    behavior
            maturity                    interaction
                │                           │
                ▼                           ▼
         organic / curved              angular / branching
         precious / gold               instrument / green
         ceremonial                    operational
```

The capability identity does not change when switching Trees.

The projection does.

---

## 2. Core visual metaphor

Yggdrasil is a monument.

Arbor is an instrument.

Yggdrasil should feel ancient, accumulated, prestigious, and grown.

Arbor should feel alive, observable, reactive, and useful.

The strongest visual contrast is therefore not primarily color.

It is geometry.

### Yggdrasil

```text
╭────○
    ╭───╯
────○
    ╰──────○
```

- curved
- flowing
- organic
- hierarchical
- ceremonial
- visually weighted toward earned standing

### Arbor

```text
────○────────┐
             └────○
        ┌──────────┘
────○───┘
```

- angular
- directional
- branching
- circuit-like
- relational
- visually weighted toward capability interaction

The Arbor silhouette should remain recognizable even if rendered monochrome.

If removing color makes Yggdrasil and Arbor difficult to distinguish, the geometry is not distinct enough.

---

## 3. Arbor world

The baseline Arbor environment is a dark behavioral instrument.

| Token | Description |
|---|---|
| GROUND | washed charcoal |
| PRIMARY | Arbor green |
| INK | warm bone |
| SECONDARY | graphite / ghost grey |
| ACTIVE | luminous green-white |
| INACTIVE | dim structural grey |

Suggested conceptual palette:

- `charcoal` `#1b1d1b` background
- `bone` `#eeeae2` primary text / highlighted nodes
- `arbor` `#55c878` canonical Arbor signal
- `arbor-bright` `#8de89b` active path
- `ghost` `#687068` secondary topology

Exact production tokens may change after accessibility review.

The important rule is semantic:

> Green belongs to Arbor itself.

It should not indicate "good", "Heaven", rank, trust, or prestige.

It means:

you are looking through the Arbor lens.

---

## 4. Geometry

Arbor should use a strict geometric branching grammar.

Preferred edge behavior:

- long straight runs
- deliberate 30° / 45° / 60° turns
- hard corners
- branching junctions
- occasional parallel tracks
- little or no Bézier softness
- controlled visual rhythm
- clear termination nodes

Reference feeling:

```text
                 ○
                 │
             ┌───┘
             │
   ○─────────┤
             │
       ┌─────┘
       │
────○──┘
```

The graph may resemble:

- dendrites
- circuit traces
- neural arborization
- crystalline fracture
- branching infrastructure

It should never become literal circuitry or literal botanical illustration.

It lives between the two.

---

## 5. Nodes

An Arbor node represents a capability's behavioral profile.

The node must not inherit Yggdrasil prestige language.

Avoid:

- stars
- rank halos
- crowns
- metallic rarity treatments
- prestige-sized nodes

Node emphasis may instead communicate:

- currently selected capability
- observation coverage
- active behavioral relationship
- runtime state
- confidence / evidence availability
- interaction participation

Possible neutral node vocabulary:

- `○` ordinary capability
- `◎` selected capability
- `◉` actively observed
- `◇` interaction junction
- `□` unresolved / incomplete projection

These glyphs are illustrative only and should not become semantic contracts before capability data is finalized.

---

## 6. Arbor edges

Edges are the real visual heart of Arbor.

Unlike Yggdrasil fusion edges, Arbor edges describe what capabilities do to one another during execution.

Expected interaction families include:

- `stabilizes`
- `amplifies`
- `conflicts`
- `recovers`
- `compresses-after`
- `unlocks`
- `duplicates`

The production visual system should reserve clearly separable edge treatments for these relationships.

Example direction:

```text
stabilizes        ─────────────
amplifies         ═════════════
conflicts         - - - - - - -
recovers          · · · · · · ·
```

Do not lock exact stroke patterns until the interaction-edge contract lands.

The design should instead establish the requirement:

> Different Arbor relationships must remain distinguishable without relying exclusively on color.

This matters for accessibility and for Hell inversion.

---

## 7. Heaven, Hell, and Ultra are runtime weather

Heaven / Hell / Ultra should not redefine the base Arbor visual identity.

They are runtime phenomena applied to Arbor.

```text
              ARBOR
         behavioral graph
                │
        ┌───────┼────────┐
        │       │        │
        ▼       ▼        ▼
     HEAVEN    HELL     ULTRA
     converge explore   govern
```

The tree remains Arbor.

The weather changes.

---

### 7.1 Heaven

Heaven represents convergence.

The tree should not simply "turn blue."

Instead, Heaven should visually indicate:

- reduced branching
- selected routes
- stabilized topology
- fewer active alternatives
- prismatic light traveling through specific branches

Conceptually:

```text
╲
─────────◎════════○────○
         ╱
```

The prism should appear as split light or signal, not as a rainbow background.

Arbor green remains visible underneath.

---

### 7.2 Hell

Hell represents exploration and widened search.

Hell should use the existing Skill Heaven inversion language rather than becoming "red Arbor."

The interaction should feel like an impact-frame polarity flip:

```text
CHARCOAL
GREEN
BONE

   ↓ impact cut

PAPER
INK
INVERTED SIGNAL
```

In Hell:

- background becomes pale / paper-like
- structural Arbor lines invert toward dark ink
- active signals become inverted-spectrum accents
- restrained red may appear at critical impact points
- topology remains recognizably the same Arbor graph

This is important:

> Hell changes the conditions, not the identity of the Tree.

The result should resemble dark fractures crossing paper.

That visual language also connects strongly to Arbor's angular structure.

---

### 7.3 Ultra

Ultra is not a third behavioral pole.

Ultra governs movement between exploration and convergence over long horizons.

Therefore Ultra should appear as activity traveling through Arbor, not as Arbor becoming gold.

Recommended treatment:

```text
green Arbor structure

      ○────────○
               ╲
                ◎━━━━━━○
                    ≋
                 gold wake
```

Gold should behave as:

- illumination
- smoke
- wake
- trace
- transient energy

Never as Arbor's base material.

This preserves the distinction:

| YGGDRASIL GOLD | ULTRA GOLD |
|---|---|
| permanent | temporary |
| material | light |
| prestige | agency |
| monument | runtime trace |

Yggdrasil is made of gold.

Ultra is lit by gold.

## 8. Tree Lens switcher

Gaia Skill Tree should treat Yggdrasil and Arbor as sibling projections inside the same product shell.

Suggested interaction:

```text
┌─────────────────────────────────────┐
│ TREE LENS                           │
│                                     │
│ [ YGGDRASIL III ]   [ ARBOR I ]     │
│    PRESTIGE          CAPABILITY     │
└─────────────────────────────────────┘
```

This is not a theme switch.

It changes the governing projection.

When the user switches Trees:

1. preserve the selected Skill identity
2. preserve relevant inspection context where practical
3. animate the graph into its new topology
4. move the selected capability to its Arbor position
5. update semantics, edge legend, filters, and metrics

Conceptually:

```text
YGGDRASIL

        ○
      ╱   ╲
    ○       ○
      ╲
       ◎
       ↑
   same Skill

      SWITCH

        ↓

ARBOR

○────────┐
         └────○────◎
      ○───────┘
               ↑
           same Skill
```

The movement is intentional.

The capability did not change.

The governing law changed.

## 9. Domain and routing

`arbor.gaiaskilltree.com` may exist as a direct entrance into the Arbor projection.

It should not feel like a separate product universe.

Preferred conceptual relationship:

```text
arbor.gaiaskilltree.com
          │
          ▼
   Gaia Skill Tree shell
          │
          ▼
      Tree = Arbor
```

The main product should continue to support moving between Trees.

Possible canonical routing:

```text
gaiaskilltree.com/tree/yggdrasil
gaiaskilltree.com/tree/arbor
```

The subdomain can deep-link to the Arbor state.

---

## 10. One Tree of many

Arbor must establish a reusable Gaia pattern:

> Every Tree may have its own visual physics.

Gaia does not need one graph aesthetic.

Gaia needs one grammar for creating graph aesthetics.

```text
GAIA
│
├── YGGDRASIL
│   material: precious metal
│   geometry: organic
│   index: prestige / trust
│
├── ARBOR
│   material: illuminated instrument
│   geometry: angular
│   index: behavior / interaction
│
├── FUTURE TREE
│   material: ?
│   geometry: ?
│   index: cost / efficiency
│
└── FUTURE TREE
    material: ?
    geometry: ?
    index: security / readiness
```

**Shared:**
- capability identity
- Gaia shell
- navigation
- inspection model
- provenance
- observations

**Tree-specific:**
- topology
- geometry
- metrics
- edge semantics
- visual material
- filtering vocabulary

## 11. UI composition

The Arbor Explorer should feel closer to an instrument panel than a fantasy map.

Suggested hierarchy:

```text
┌───────────────────────────────────────────────┐
│ Gaia Skill Tree        TREE LENS: ARBOR I     │
├───────────────────────────────────────────────┤
│                                               │
│              CAPABILITY GRAPH                 │
│                                               │
│              angular Arbor                    │
│                                               │
│                                               │
│                              ┌──────────────┐  │
│                              │ INSPECTOR    │  │
│                              │ capability   │  │
│                              │ behaviors    │  │
│                              │ evidence     │  │
│                              └──────────────┘  │
│                                               │
├───────────────────────────────────────────────┤
│ relationship legend        runtime weather    │
└───────────────────────────────────────────────┘
```

Avoid overwhelming dashboards around the graph.

The Tree remains the hero.

Controls should feel like instrumentation attached to it.

---

## 12. Motion language

Arbor motion should communicate state change and propagation.

Preferred motion:

- signals travel along edges
- nodes pulse when observations activate them
- related branches illuminate sequentially
- switching Trees visibly reprojects topology
- Hell uses a hard impact cut
- Heaven collapses / narrows activity
- Ultra leaves transient trail effects

Avoid:

- idle floating particles everywhere
- constant node wobble
- breathing neon
- random background motion
- excessive easing
- decorative animation disconnected from data

Motion should answer:

> What changed?

---

## 13. Density

The concept images intentionally exaggerate density to establish the visual world.

Production should prioritize legibility.

The graph should have multiple density levels:

- **FAR:** tree silhouette, major behavioral regions
- **MID:** capabilities, primary relationships
- **NEAR:** interaction semantics, receipts, behavioral profile, provenance

Do not attempt to display every observation and edge simultaneously.

The graph should reveal detail progressively.

---

## 14. Data binding strategy

The frontend should be designed before capability data is complete, but should not fabricate semantics.

Until Arbor projections land:

### Safe to implement now

- Arbor visual tokens
- angular geometry primitives
- graph shell
- Tree Lens switcher
- responsive layout
- node selection model
- inspector shell
- relationship legend component
- runtime-weather framework
- Heaven / Hell / Ultra visual state machinery
- mock topology clearly marked as prototype data

### Must remain data-driven later

- node placement
- behavioral categories
- interaction-edge types
- interaction strength
- HH-derived properties
- benchmark coverage
- support status
- active interpretations
- runtime observations

The UI must not encode guessed semantics into layout logic.

---

## 15. Placeholder strategy

Prototype data may exist only to validate the visual system.

It must be obvious in code that it is temporary.

Suggested boundary:

```text
ArborProjection
      │
      ├── prototype adapter
      │      └── fixture graph
      │
      └── production adapter
             └── Arbor projection data
```

When real capability data lands, the renderer should not need to be rewritten.

Only the data adapter and semantic mapping should change.

---

## 16. Design invariants

The first implementation should protect these.

- **INV-1:** Arbor must remain visually distinguishable from Yggdrasil without color.
- **INV-2:** Arbor must not use stars, ranks, or prestige language as its primary visualization.
- **INV-3:** Arbor edges must be able to encode multiple behavioral relationship types.
- **INV-4:** Relationship meaning must never depend on color alone.
- **INV-5:** Hell is an inversion / impact state, not simply a red theme.
- **INV-6:** Heaven does not repaint Arbor blue.
- **INV-7:** Ultra gold is transient illumination, never Arbor's structural material.
- **INV-8:** Tree switching preserves Skill identity.
- **INV-9:** A Skill is allowed to occupy radically different positions in different Trees.
- **INV-10:** Arbor must remain extensible to real interaction edges once the data contract lands.
- **INV-11:** Prototype topology must never silently become canonical Arbor semantics.
- **INV-12:** The Tree itself remains the primary visual object. UI chrome is subordinate.

---

## 17. Anti-goals

Do not build:

- Yggdrasil with green CSS
- a generic force-directed graph with different colors
- a Matrix-style neon visualization
- an RPG rarity tree
- red Hell / blue Heaven / gold Ultra skins
- a dashboard where the graph is secondary
- dozens of invented behavioral metrics
- fake interaction relationships before the contract exists
- permanent topology based on prototype fixtures
- a separate Arbor product identity disconnected from Gaia Skill Tree

---

## 18. Accessibility

The production implementation should support:

- WCAG-compliant text contrast
- relationship differentiation by stroke / glyph, not color only
- reduced-motion mode
- keyboard node navigation
- visible focus state
- textual relationship descriptions
- Hell inversion that preserves readable contrast
- no essential information communicated only by animation

---

## 19. North Star

The intended emotional distinction is:

### YGGDRASIL III
*"What has this capability earned?"*

```text
        GOLD
       ╭────╮
    ╭──╯    ╰──╮
   ○            ○
```

- prestige
- history
- standing
- monument

### ARBOR I
*"What does this capability do?"*

```text
GREEN / BONE
────○──────┐
           └────○
      ┌─────────┘
```

- behavior
- interaction
- runtime
- instrument

The shortest version of the design thesis:

> Yggdrasil is the monument Gaia grows around proven capability. Arbor is the instrument Gaia uses to observe capability in motion.

Or, visually:

> Gold curves versus green fractures. Prestige versus behavior. Permanent structure versus runtime weather.

---

## 20. Readiness target

This issue does not require final Arbor capability data.

It should leave the frontend ready so that when the projection lands, Gaia can move from:

```text
prototype fixture
       ↓
Arbor renderer
```

to:

```text
canonical Arbor projection
       ↓
same Arbor renderer
```

without redesigning the Tree.

The design work is successful when the visual language, projection shell, and interaction grammar are already mature enough that real capability data feels like it was always meant to live there.
