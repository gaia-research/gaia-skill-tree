1

gaia-curate — Discover & package the skill

You have found a real repo with a SKILL.md. Your job is to run the prefill, let the worker map it to a generic, validate the packet, and write it to the review folder. Nothing touches the registry yet.

Step 1 — Preflight: check auth & tools
bash
# confirm gaia CLI is installed
gaia --version

# confirm gh CLI is authenticated
gh auth status

# confirm python3 available
python3 --version
Step 2 — Snapshot the generic list (save this file — you need it for validation)
bash
gaia dev list --generic --json > /tmp/generic-snapshot.json

# verify it produced output
wc -l /tmp/generic-snapshot.json
ℹ This snapshot is the trust anchor for packet validation. Keep it. Don't overwrite it mid-run.
Step 3 — Run the prefill against the candidate SKILL.md URL
bash
# Replace the URL with the real blob URL of the upstream SKILL.md
gaia dev prefill \
  --source "https://github.com/owner/repo/blob/main/SKILL.md" \
  --output /tmp/prefill-output.json

# Inspect the result — check nStrong / nTotal / matchTier values
cat /tmp/prefill-output.json | python3 -m json.tool | head -80
Step 4 — Apply the mapping decision rules (no judgment — just the rules)
Rule (first match wins) Decision When
1NOT_A_SKILLartifactGate != "valid-skill"
2DUPLICATEexactDedupe != null
3DEFERambiguity != null
4NEW_GENERICnTotal == 0
5MAPnStrong == 1 → use that genericId
6DEFEReverything else (weak only, or nStrong ≥ 2)
ℹ Count nStrong = number of entries with matchTier == "strong" in mappingOptions[]. Count nTotal = total entries. Do not re-rank.
Step 5 — Write the discovery-packet-v2 JSON

Create the packet at a path like registry-for-review/discovery-packets/owner--skill-name.json. Minimum required fields:

json skeleton
{
  "schemaVersion": "discovery-packet-v2",
  "source": {
    "url": "https://github.com/owner/repo/blob/main/SKILL.md",
    "canonicalUrl": "https://github.com/owner/repo/blob/main/SKILL.md",
    "retrievedAt": "2025-01-15T10:00:00Z",
    "lane": "github-skill-file"
  },
  "normalized": {
    "name": "Skill Name From Frontmatter",
    "description": "Description from frontmatter — verbatim",
    "hostRepository": "https://github.com/owner/repo"
  },
  "contentSha256": "<sha256 of the SKILL.md content>",
  "exactDedupe": null,
  "mappingOptions": [
    /* copy from prefill-output.json */
  ],
  "decision": "MAP",
  "reasonCode": "MAP_EXISTING_GENERIC",
  "selectedGenericId": "the-generic-id-from-strong-option",
  "genericSnapshot": {
    "command": "gaia dev list --generic --json",
    "capturedAt": "2025-01-15T10:00:00Z",
    "contentSha256": "<sha256 of canonical JSON of that snapshot>",
    "generics": [/* contents of /tmp/generic-snapshot.json */]
  },
  "lifecycle": "review-ready"
}
✓ For contentSha256 of the generic snapshot: python3 -c "import json,hashlib; d=json.load(open('/tmp/generic-snapshot.json')); print(hashlib.sha256(json.dumps(d,sort_keys=True,separators=(',',':')).encode()).hexdigest())"
Step 6 — Validate the packet
bash
python3 scripts/validate_discovery_packet.py \
  --generic-snapshot /tmp/generic-snapshot.json \
  registry-for-review/discovery-packets/owner--skill-name.json

# Must exit 0 with no MALFORMED_PACKET or MISSING_REQUIRED_FIELD errors
🛑
Stop — L4 Human Gate

The packet is now in registry-for-review/discovery-packets/. Review it carefully before proceeding. The next step mutates the packet — you cannot un-write it to the registry once pushed.

2

L4 Review — You ratify the topology

No one else does this. You are the human reviewing the packet and appending l4Resolution. This is the only place where new generic IDs, named skill identity, and exact upstream URLs get locked.

What to check
  • The mapping decision is correct — does selectedGenericId match the skill's actual capability?
  • If NEW_GENERIC: is the proposed generic name and description vendor-neutral and falsifiable?
  • The source.url is a real blob/ GitHub URL (not a tree/ or a listing page).
  • The normalized.description is verbatim from the SKILL.md frontmatter — not paraphrased.
  • The similarity score (mappingOptions[].similarity) and matchTier make sense for the mapping.
Append l4Resolution to the packet

Open the JSON file and add this block at the top level:

json — append to packet
"l4Resolution": {
  "generic": {
    "id": "the-final-generic-id",
    "name": "Human Readable Generic Name",
    "description": "Vendor-neutral, falsifiable, one paragraph.",
    "type": "basic",
    "prerequisites": []
  },
  "named": {
    "contributor": "github-handle",
    "skillName": "kebab-case-skill-name"
  },
  "upstreamSkillFileUrl": "https://github.com/owner/repo/blob/main/SKILL.md"
}
Re-validate after appending l4Resolution
bash
python3 scripts/validate_discovery_packet.py \
  --generic-snapshot /tmp/generic-snapshot.json \
  registry-for-review/discovery-packets/owner--skill-name.json

gaia push → Draft PR — Materialize the intake issue + branch

Step 1 — Create the review branch
bash
# Use the convention: review/meta/<contributor>--<skill-name>
git checkout -b review/meta/github-handle--skill-name
Step 2 — Run gaia push to validate + open intake issue
bash
# Dry run first — preview without writing anything
gaia push \
  --from-file registry-for-review/discovery-packets/owner--skill-name.json \
  --dry-run

# If dry run looks good — run for real (opens GitHub intake issue)
gaia push \
  --from-file registry-for-review/discovery-packets/owner--skill-name.json

# Note the issue number printed — you need it for the PR
ℹ gaia push validates the frozen generic snapshot, rejects canonical duplicates, and opens the intake issue. It does not write to registry/ yet.
Step 3 — Commit the packet and open a draft PR
bash
git add registry-for-review/discovery-packets/owner--skill-name.json
git commit -m "feat(intake): curate contributor/skill-name [closes #ISSUE]"
git push -u origin review/meta/github-handle--skill-name

# Write the PR body to a temp file (avoids shell quoting issues)
cat > /tmp/pr-body.md <<'EOF'
## Intake: contributor/skill-name

Closes #ISSUE

### What this does
- Discovery packet for `contributor/skill-name` (generic: `the-generic-id`)
- L4 reviewed and approved
- ev-pipeline + ingest to follow on this branch

### Checklist
- [x] Packet validated (exit 0)
- [x] l4Resolution appended
- [ ] ev-pipeline run
- [ ] gaia-ingest complete
- [ ] TM appraised + calibration approved
EOF

gh pr create \
  --draft \
  --title "feat(intake): curate contributor/skill-name" \
  --body-file /tmp/pr-body.md

# Note the PR number printed
gh pr view --json number,url
Step 4 — Apply labels to the PR and the intake issue

The intake:* labels are machine gates — the intake-approval.yml workflow watches for them and fires automatically. Apply them in order; do not skip ahead.

LabelApplied toWho appliesWhat it triggers
intakeIssue + PRAuto (gaia push) or youRoutes into the intake queue
needs-triageIssueAuto (gaia push)Marks it as awaiting review
intake:topology-approvedIssueMaintainer onlyFires workflow: adds intake:evidence-review, removes needs-triage, posts handoff comment
intake:evidence-reviewIssueAuto (workflow)Signals agent to prepare Stage-1 seed + Phase-0 plan
intake:evidence-readyIssueAgent / youSignals evidence plan is ready for human approval
intake:evidence-approvedIssueMaintainer onlyFires workflow: opens the single draft review/meta/intake-<N> PR
intake:rejectedIssueMaintainer onlyCloses intake; no promotion automation fires
human-proposalPRAuto (triage workflow)Routes non-bot PRs for human review
needs-reviewPRAuto (triage workflow)Signals PR needs a reviewer
ℹ intake:topology-approved and intake:evidence-approved are maintainer-only — the workflow checks your repo permission and rejects the label if you're not admin, maintain, or write. Also: intake:evidence-approved requires both intake:evidence-review and intake:evidence-ready to be present or the workflow errors.
bash — label the PR (auto-triage usually does this, but if not:)
gh pr edit <PR_NUMBER> \
  --add-label "intake" \
  --add-label "human-proposal" \
  --add-label "needs-review"

# Verify labels landed correctly
gh pr view <PR_NUMBER> --json labels --jq '.labels[].name'

# When you (as maintainer) are ready to approve the topology:
gh issue edit <ISSUE_NUMBER> --add-label "intake:topology-approved"
# ↑ This fires intake-approval.yml automatically — it adds intake:evidence-review
#   and removes needs-triage. Watch it at: gh run list --workflow=intake-approval.yml

ev-pipeline — Verify evidence before ingesting

You run each phase manually. The pipeline operates on evidence/by-type/ files — it never touches registry/. Each phase produces review artifacts; you decide what to approve.

Phase 0 — ev-discovery: find Stage-2 evidence (skippable — run only on declared need)

Phase 0 is the only phase that searches the web for new evidence. Skip it for a routine Stage-1 intake. Run it when you need benchmark-result, arxiv, peer-review, or richer social-signal rows — e.g. when trying to promote a skill to 3★+.

⚠ Requires FIRECRAWL_API_KEY in your environment. If absent, skip this phase entirely.
bash — discover Stage-2 evidence for one skill
# Confirm key is set
echo $FIRECRAWL_API_KEY

# Run discovery — declare the evidence types you need
# Valid Stage-2 types: benchmark-result, arxiv, peer-review, social-signal
gaia dev discover \
  --skill contributor/skill-id \
  --repo "https://github.com/owner/repo" \
  --types benchmark-result,arxiv,peer-review,social-signal \
  --output evidence/discovery/contributor--skill-id.md

# Review discovered rows — do NOT commit them yet
cat evidence/discovery/contributor--skill-id.md

Benchmark candidates — special rule: if discovery finds a vendor benchmark page, it becomes a candidate for Phase 2B, not a scoring row. It only scores after: (1) you promote it in registry/benchmark-sources.json, (2) reproducibility fields are verified, (3) you approve it in Phase 2B. After reviewing, append the rows you want into the appropriate source input files so Phase 1 picks them up.

Phase 1 — ev-collection: build the type-first evidence lake
⚠ This runs on the entire registry — not just your new skill. generate_source_dump.py reads all named-skill evidence rows and all collector channels for every skill in registry/named/. You are refreshing the whole lake. Your new skill's rows will appear in the output alongside all other skills. That is expected and correct.
bash
# Generates evidence/by-type/*.md — reads the WHOLE registry
python3 evidence/scripts/generate_source_dump.py \
  --output-dir evidence \
  --by-type-dir evidence/by-type

# Compiles unified lake from by-type files
python3 evidence/scripts/compile_data_lake.py \
  --sources evidence/by-type \
  --lake evidence

# Verify primary outputs exist
ls evidence/by-type/
ls evidence/unified_evidence_lake.md
Phase 2 — ev-star-verification: verify live GitHub star counts
bash
# Check auth first — zero stars from an unauth'd call is poison data
gh auth status

# For each github-stars-own row in evidence/by-type/github-stars-own.md,
# fetch the live count and compare:
gh api repos/OWNER/REPO --jq '.stargazers_count'

# Flag any row where recorded stars differ from live count.
# Do NOT silently update — note them in your source report.
ℹ If stars differ by >10%: add a note in the source report. Don't auto-correct; that's for the ingest step under your explicit approval.
Phase 2B — ev-benchmark-verification: classify benchmark rows (if any)
bash
# Only needed if the skill has benchmark-result evidence
# Check whether the benchmarkId is in the catalog:
cat registry/benchmark-sources.json \
  | python3 -m json.tool \
  | grep "the-benchmark-id"

# Lane classification:
#   "verified"  = CI/verifier reproduced  → 2.0x multiplier
#   "reported"  = public claim accepted   → 1.0x multiplier
#   "rejected"  = blacklisted / no proof  → 0x (skip)
Phase 3 — ev-adversarial-audit: check for bad data

Read each evidence/by-type/<type>.md and flag:

  • Dead or malformed URLs — especially GitHub tree/ where blob/ is required
  • Subjective wording not backed by source ("elite", "high-quality", "leading")
  • Evidence type mismatches (e.g. a social-signal row that is really a peer-review)
  • Star counts that conflict with Phase 2 live results
  • Benchmark rows citing unregistered or rejected benchmark IDs
  • arXiv rows with 0 citations — these contribute 0 TM; note them explicitly
bash — check URL format issues
# Find any github tree/ URLs that should be blob/
grep -rn "github.com/.*/tree/" evidence/by-type/

# Find subjective words in evidence notes
grep -rni "elite\|high-quality\|best-in-class\|leading" evidence/by-type/
Phase 4 — ev-link-validation: check URL health
bash
# Run the coexistence URL health shim
python3 evidence/scripts/validate_sources.py

# Or a 10-URL sample first to test
python3 evidence/scripts/validate_sources.py 10

# 404 / timeout / connection-refused = dead link → remove that row before ingest
🛑
Human Evidence Gate

Review the source report from Phases 1–4. Approve the rows you want to ingest. Remove any dead-link, subjective, or mismatched rows. Only pass live, correctly scoped rows to Phase 5.

gaia-ingest — Write evidence to the named skill

This is the first time you mutate registry/. Every row uses --no-build. You run one build at the end. Then you appraise TM and calibrate stars — but you never run gaia dev calibrate without your own explicit approval.

Step 1 — Confirm the named skill file exists
bash
# Does the named skill node exist?
ls registry/named/<contributor>/<skill-id>.md

# If it does NOT exist — create it first:
GAIA_OPERATOR_OVERRIDE=1 gaia dev named \
  --contributor github-handle \
  --skill kebab-case-skill-name \
  --generic the-generic-id \
  --upstream "https://github.com/owner/repo/blob/main/SKILL.md" \
  --no-build

# Inspect what's already there
sed -n '1,80p' registry/named/<contributor>/<skill-id>.md
Step 2 — Ingest each approved evidence row (one command per row, all --no-build)
bash — repo-own row
GAIA_OPERATOR_OVERRIDE=1 gaia dev evidence contributor/skill-id \
  "https://github.com/owner/repo" \
  --type repo-own \
  --commits 847 \
  --contributors 12 \
  --notes "Official upstream repo. Commit/contributor counts verified via GitHub API." \
  --source-started-at 2024-03-01 \
  --no-build
bash — github-stars-own row
GAIA_OPERATOR_OVERRIDE=1 gaia dev evidence contributor/skill-id \
  "https://github.com/owner/repo/blob/main/SKILL.md" \
  --type github-stars-own \
  --stars 3421 \
  --skill-count-in-repo 1 \
  --notes "Official SKILL.md. Star count verified live via gh api." \
  --source-started-at 2024-03-01 \
  --no-build
bash — self-attestation row (Stage 1 baseline)
GAIA_OPERATOR_OVERRIDE=1 gaia dev evidence contributor/skill-id \
  "https://github.com/owner/repo/blob/main/SKILL.md" \
  --type self-attestation \
  --notes "Contributor's own SKILL.md — baseline self-attestation." \
  --source-started-at 2024-03-01 \
  --no-build
bash — social-signal row (e.g. YouTube view count)
# Only if view count is PUBLICLY VISIBLE on the source page.
# If you cannot see it, do not ingest it.
GAIA_OPERATOR_OVERRIDE=1 gaia dev evidence contributor/skill-id \
  "https://www.youtube.com/watch?v=XXXX" \
  --type social-signal \
  --views 8510 \
  --notes "Third-party tutorial demonstrating the skill. View count verified on source page." \
  --source-started-at 2025-01-10 \
  --no-build
ℹ To see all supported flags for a type: gaia dev evidence --help

Common errors — and exactly what to do

UNTRUSTED_GENERIC_SNAPSHOT

The contentSha256 in the packet doesn't match the file you're passing to --generic-snapshot.

fix
# Recompute the sha256 from your saved snapshot file:
python3 -c "import json,hashlib; d=json.load(open('/tmp/generic-snapshot.json')); \
print(hashlib.sha256(json.dumps(d,sort_keys=True,separators=(',',':')).encode()).hexdigest())"
# Paste that value into genericSnapshot.contentSha256 in your packet.
INVALID_GENERIC_SELECTION — mapped ID not in snapshot

You used a genericId that wasn't in the snapshot you captured. Either re-capture the snapshot after adding the new generic, or use the id that's actually there.

gaia dev evidence fails — "unknown evidence type"
fix
gaia dev evidence --help
# Lists all supported --type values and their required flags
gaia dev validate fails after ingest
fix
GAIA_OPERATOR_OVERRIDE=1 gaia dev validate --verbose
# Read the first error carefully — usually a missing required field or
# a schema mismatch. Fix the named skill file, then re-run validate.
"view count not publicly available" — social-signal ingest rejected

Do not fabricate view counts. If you can't see the count on the source page, omit the --views flag or skip the row entirely. A row without a verifiable view count does not score.
