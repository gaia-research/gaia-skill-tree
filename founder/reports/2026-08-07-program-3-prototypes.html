Install parity — the correction that mattered

Summon originally fetched a single SKILL.md over HTTP. That is not how Gaia installs skills, and it silently produces broken ones: many skills are directories — SKILL.md plus reference/, scripts/, fixtures. A summoned skill missing its scripts is a description of a skill, not a skill.

Summon now mirrors gaia install: parse the GitHub URL the same way, shallow-clone the source repo, validate that the resolved subpath exists and is a directory containing SKILL.md, then materialize the whole directory. Suites recurse. Session-locking is preserved by putting the git cache inside the session root, so nothing outside the session is touched.

Proof it works — garrytan/review comes down as 13 files including a specialists/ subdirectory, not one lone file.

Then the clone had to go

Install parity worked, and immediately created a new problem: 247 MB of orphaned session roots filled the machine and killed a running worker with ENOSPC. Cloning repos means a session root is repo-sized, and the high-entropy rungs are defined by summoning more — so the most valuable mode allocates the most disk fastest.

The ratio that solved it: the clone is ~100 MB, the skill inside it is ~200 KB. We were keeping the crate to store the envelope. Discard the clone after extraction, reap abandoned roots on every summon (with a signal-0 PID check so a live session is never collected), and retain only extracted payloads in a bounded 16 MiB LRU cache keyed by resolved commit SHA.

 beforeafter
session root69–101 MB212 KB
re-summon after the session was destroyedfull re-clone0.831 s

The founder's instinct to keep this "in memory" was right, and the mechanism is simpler than a daemon: at this size the OS page cache holds hot payloads in RAM anyway, so an on-disk payload store is memory-resident in every way that matters — without owning a background process or a crash lifecycle. A RAM disk lost on portability; a daemon lost on complexity.

A prior of mine was disproved, correctly. I expected sparse/partial checkout to be the real fix. Measured across three skills it gave smaller transient peaks but was slower every time. The worker rejected my hint on evidence.

Hermes hides its skills on disk, not behind a flag

Hermes resisted every documented suppression flag — --safe-mode, --ignore-rules, --ignore-user-config all still reported 108 skills, despite --ignore-rules claiming to skip "preloaded skills". The worker probed it, failed to find a clean floor, and honestly shipped a recipe-only door rather than overclaim.

The reason turned out to be structural: those 108 are bundled skills already seeded onto disk inside the profile. They are not injected at runtime, so no runtime flag can remove them — by the time a session starts they are simply files the profile owns. --safe-mode suppresses customizations; seeded bundled skills are not customizations.

Confirmed in the Hermes source: hermes_constants.py:63 resolves HERMES_HOME from the process environment, and skills_sync.py:1269 writes a .no-bundled-skills marker into it that yields "zero bundled-skill seeding". So the clean room is a filesystem problem, not a flag problem — which is the shape the compiler's fsPlan already handles, exactly as codex-heaven scopes CODEX_HOME. A session-scoped home with the marker pre-written gives a true floor while never touching the real profile.

Architecture

Core and quirks

Five doors in, the boundary is clear enough to name — so adding harness six is a table row and a probe, not a redesign.

The correction that mattered: a door does not suppress "skills", it suppresses context sources — skills, rule and instruction files, memory, prompt templates, toolsets, plugins and MCP, subagents. That narrow early framing is exactly why Hermes and Grok both surprised us. Cursor's .cursorrules is the next instance and it drops into the matrix without touching the ladder.

Core owns the ladder, the postures, the P2/P3/D12/M0 guarantees, the compiler, the summon engine, measurement, and the door package shape. Quirks own which mechanism class a harness is, its flags, its auth file, whether skills load mid-session, extra rule surfaces, and whether it reads another harness's directories.

The boundary carries a falsifiable test: if adding a door needs core edits beyond a switch case, the abstraction is leaking — fix it before the sixth door bakes it in.

Two gaps worth knowing. off still aliases to floor, the doorless benchmark ruler, rather than product-floor, the launchable one — that is skill-heaven #24 and it is a small fix. And the four Hell rungs currently refuse rather than compose; wiring them to the summon engine is what turns a gate into a product.

Not the same axis. Several harnesses ship a reasoning dial with level names that look identical to these rungs — pi's --thinking, codex's model_reasoning_effort, Hermes' --reasoning (which even carries an ultra). Those set how hard the model reasons. This ladder is skill- and context-scoped — what gets admitted into the session. The shared vocabulary is coincidence. Reasoning effort is a control variable to hold constant across benchmark arms, never the thing under test; treating the two as one axis would produce meaningless measurements.

Instrumentation

herdr is the benchmarking environment

Every worker, probe, and benchmark arm runs in a pane you can watch. Nothing hidden, including nested subagents.

This became a written rule after a worker was caught probing pi through its own Bash tool, hiding which --model actually ran. Rule 0: no harness invocation goes through an agent's shell tool — it runs in a pane with the argv on screen. A probe the operator could not see is not evidence.

The refusal worth keeping

The correction was first sent to the worker mid-turn. It refused — reasoning that an unexpected instruction changing its execution path had the shape of a prompt injection — and kept following its written brief. It refused a second time when the founder typed the same thing directly into its pane.

That was the right call, and the fix was the channel rather than the worker. Execution rules now live in CLAUDE.md, loaded as project context before work starts, alongside an explicit endorsement of continuing to refuse mid-turn redirects. The pane is a window, not a control channel.
